# 裁决：AT-BD-001 的 GUI 侧解释

日期：2026-10-17
范围：`crates/gui/src/state/profile.rs`、`crates/gui/src/views/profiles_view.rs`、`tools/at_coverage.py`
规格：`docs/specs/25_ACCEPTANCE_TESTS.md` 的 AT-BD-001、`docs/specs/09` §6

## 1 要求是什么

> AT-BD-001：严格 Blu-ray profile 禁止 2160p PGS；**UI 明确解释**。

规格原文把这个要求拆成两半：CLI 侧拒绝（已实现、已实测），GUI 侧要**明确解释**。
此前 `tools/at_coverage.py` 把 AT-BD-001 记为 `shared`（"由更宽用例覆盖"），
理由是 GUI 那半没做。本次把它做完。

拒绝层本来就有专属用例（记录一下就够，无需另写）：
`codec-pgs/src/encoder.rs` 的 `invalid_inputs_are_rejected_before_any_segment_is_written`
断言 3840 宽报 `STK-PGS-0091`，且**写任何段之前**就拒；
另有 `core-model/src/canvas.rs` 的 `bluray_bounds_reject_2160_pgs`
与 `core-model/src/profile.rs::validate`（`STK-VAL-0002`）。

## 2 抳出的真缺陷：出厂默认 profile 自己跑不起来

给 GUI 加校验时立刻发现：**出厂的第二个默认 profile 是 2160p PGS**。

```
OutputProfile::default_uhd_sup()
  name: "2160p 4K HDR SUP"
  target_format: Pgs
  canvas: Uhd2160
```

而 CLI 的 `pgs encode` 默认 `--level standard`（`crates/cli/src/args.rs` 断言
`level == ValidationLevel::Standard`），标准级 PGS 不允许 3840×2160。

后端实测（真 libass）：

```
$ subtitletool-cli pgs encode probe.ass --canvas 3840x2160 --out old.sup
STK-PGS-0091: 画布超出 Blu-ray PGS profile 上限 1920x1080
  建议：更大画布只能作为非标准实验输出，禁止标注 Blu-ray/UHD-BD compliant（09 §8）
```

即：**用户装好程序、什么都不改、直接排队，第一个 profile 就会失败。**

这是最坏的一种默认值。用户不会想到"我选的画布不对"（他没选过任何东西），
他会认为程序坏了。而且这个失败发生在**批量执行的中途**，不是配置阶段。

### 修法

默认改为 `1080p HDR SUP`（`default_hdr_sup`），画布 `Fhd1080`，
`custom_suffix` 从 `.4k.sup` 改为 `.hdr.sup`，名字同步改。

**HDR 映射保留 `ReferenceWhite(203)`** —— 那是这个 profile 存在的理由
（"HDR SUP"），它不是 2160p 的副产品，不该跟着一起丢。

想要 4K 的用户可以自己把画布改成 3840×2160，那时 `problem()` 会明确告诉他
为什么不行、以及可以怎么改。**这是"拦下来并解释"，不是"悄悄不让他选"。**

修完实测（真 libass）：

```
$ subtitletool-cli pgs encode probe.ass --canvas 1920x1080 --out new1080.sup
ok  pgs encode
{ "bytes": 5117, "canvas": "1920x1080", "no_blocking_findings": true, ... }
产物前 2 字节: 50 47  ("PG")
```

## 3 校验为什么不重新实现

`problem()` **不自己判断**"2160p 行不行"，而是调用 `core_model::Canvas::within_bluray`。

理由是组件级单一事实源：同一条规则在 CLI 侧是
`core_model::profile::OutputProfile::validate`（`STK-VAL-0002`），在 BDN 编码器里是
`build.rs` / `loss.rs` 的 `within_bluray`，在媒体探测里是 `suggest.rs`。
再写第三份的后果是**两边会逐渐不一致**：用户能在一个前端建出另一个前端拒绝的
profile，而两个都声称自己对。

有一条用例专门钉这件事（`gui_agrees_with_the_core_rule_it_reuses`）：
遍历 3 种画布 × 2 种位图格式，断言 `profile.is_runnable() == canvas.within_bluray()`。
**GUI 若哪天偷偷多出一套自己的规则，这条会红。**

## 4 判据覆盖哪些组合（以及刻意不覆盖哪些）

| 格式 | 画布 | 结论 | 依据 |
| --- | --- | --- | --- |
| PGS / BDN | 2160p | 拒 | 蓝光规范的位图字幕 ≤ 1920×1080 |
| PGS / BDN | 1080p、720p | 放 | 恰在上限内 |
| ASS / SRT | 2160p | 放 | 文本格式没有蓝光的画布上限 |
| 任意 | 保持原尺寸 / 自定义 | **放**（不判定） | 要到真脚本或具体取值才知道，这里不猜 |

最后一行是刻意的：`KeepOriginal` 与 `Custom` 无法在配置阶段判定，
**猜错会把能跑的活儿拦下来**。宁可在真跑时按后端的既有错误报出来
（后端本来就有 `STK-PGS-0091` 这条路径），也不在这里做假判定。

关于 BDN 为什么跟 PGS 同一条限制：BDN XML + PNG 与 PGS 是同一族的蓝光位图
交换格式，蓝光同样不允许 2160p。这个判断写进代码注释了，因为它是**一条规格解读**，
不是自明的。

## 5 UI 怎么"明确解释"

`profiles_view.rs` 里有三处改动：

1. **删掉一行假话**。原本是：

   ```rust
   text(if profile.target_format == TargetFormat::Pgs {
       "Basic PGS: 具备 (自适应量化)"
   } else {
       "标准交换格式 (无合规锁死)"
   })
   ```

   这句话**无条件**这么说出口——包括 2160p + 严格蓝光那个组合，而那正是
   AT-BD-001 要求必须解释的情形。现在改成按 `problem()` 的真实判定显示
   "符合 09 §6 的硬规则" 或 "不合规：看下方说明"。

2. **展开的卡片里显示完整说明**：原因 + 两条可选改法。

3. **警告框只在 `problem()` 有值时出现**，不是写死的文案。

说明文本覆盖三件事，用例逐条断言：哪个格式（`PGS`）、实际画布（`3840x2160`）、
可用尺寸（`1920x1080`）。**光说"无效"不算"明确解释"** —— 用户得知道怎么改。

## 7 顺带说明的事

`AT-BD-001` 在规格里有后半句：**"不得把该拒绝测试当成其他 Profile 合规证明。"**
本次没有违反它：新增的用例只断言"这个组合被拒 / 那个组合放行"，
**没有**声称任何 profile 是"合规的"。`no_blocking_findings` 与
`strict_badge_allowed` 是后端的输出，GUI 不代为声明。
