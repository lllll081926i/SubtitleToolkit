## libass 来源与真实缺陷

用户提供 `third_party/libass-9.dll`，并授权从 `D:\xia\mingw-w64-ucrt-x86_64-libass-0.17.5-1-any.pkg` 复制所需文件。该目录缺少依赖 DLL，依据其 `.BUILDINFO` 从 MSYS2 官方 UCRT64 仓库补齐对应版本；按 PE 导入图只复制 20 个运行 DLL。

官方 libass 包 SHA-256 与[包页面](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-libass)公布的 `4385fd47…5e75762` 一致。用户 DLL 与包内文件摘要均为 `cb2b4613…b8dc6b`。包元数据、许可证材料和完整逐 DLL/包哈希见[运行库锁](../../third_party/LIBASS_RUNTIME_LOCK.json)。依赖包从官方 HTTPS 获取并锁定，未验证 detached signature，也未完成产品分发许可审计。

首次强制真实 host 测试因缺 DLL 依赖失败。依赖补齐后的宿主测试又发现 `Provider::load_script` 把 `"subtitle"` 传入 `ass_read_memory` 的 codepage 参数；启用 iconv 的构建拒绝该编码名。修复为显式 `UTF-8`。现有真实加载、像素、字体注入与宿主故障用例覆盖该修复，不以静态脚本代替运行验证。

完整工作区首次强制启用 libass 后，CLI `doctor` 集成测试的成功分支仍断言协议版本 1。当前公开协议为版本 2；改为比较 `renderer_host::protocol::API_VERSION`。这是旧测试合同修正，不降低真实握手、位数、摘要或像素断言。
